# CBoard 公共沟通板发布复用与微信端安全适配

## 结论

图语家不新建第二套公共图库后端。本轮直接复用 CBoard 已有账号、媒体上传、沟通板创建、公开状态、公共板链接和删除接口，在微信小程序“照护设置 → 图片库维护”中增加受控发布入口。家属可以把自己建立的一块个人板及其可达个人子板发布为 CBoard 公共沟通板；患者表达页不会出现发布入口，也不会自动上传任何内容。

本轮完成的是“整块公共沟通板发布”，不是“逐图投稿审核平台”。逐图待审、敏感内容审核、申诉、撤回传播副本和运营队列仍没有成熟可复用的上游契约，因此继续保持独立边界。

## 变动 1：共享发布计划与许可边界

- **意图：** 把个人板图、媒体、许可和服务器 ID 映射变成平台无关、可测试的纯核心，避免微信 UI 直接拼接 CBoard API payload。
- **决策：** 在 CBoard 中性 `communicationSupport` 层新增发布计划：只接受 `device_private_board_` 个人板，遍历所选根板及其可达个人子板，拒绝内置、导入或缺失板链接；最多 100 块板、5000 张图卡；图片、录音和短视频按源地址去重。已有 ARASAAC 等公开归因原样保留；设备私有或无公开归因的素材必须由贡献者署名，并按 CC BY 4.0 发布。
- **理由：** CBoard BoardDTO/TileDTO 已经是双端唯一运行模型。把转换放在共享纯核心，可以让 Web、微信和未来原生端复用同一边界，也能在任何网络请求前拒绝错误板图与不完整素材。
- **证据：** `publicBoardPublication.test.js` 的 5 条测试全部通过，覆盖可达板图、媒体去重、私有草稿、板链接与媒体重映射、公开归因保留、授权/隐私拒绝和内置板链接拒绝。
- **生效范围：** CBoard 跨端 communicationSupport 核心和微信发布服务；不修改默认板、患者表达、分词、matcher、AI、历史或现有公共板读取协议。

## 变动 2：复用 cboard-api 的两阶段发布与失败回滚

- **意图：** 避免板树发布到一半时留下公开根板、断链子板或重复媒体，同时不新增专用发布 API。
- **决策：** 微信端先为所有板创建 `isPublic=false` 的私有占位板，再去重上传媒体，随后先发布子板、最后发布根板。任何创建、上传或更新失败时，按创建逆序调用现有删除接口，尽力撤回本次产生的板。API 未配置、未登录或预检未通过时不发出网络请求。
- **理由：** 现有 CBoard API 已有足够的通用原子操作，但没有整棵板树事务。客户端两阶段编排能完整复用成熟接口，并把公开可见窗口缩到最小；根板最后公开可以避免用户先进入尚未完成的板树。
- **证据：** 微信 port/service 共 6 条测试通过，验证原生 `/media`、`/board` 路径、HTTPS 媒体结果、私有占位、媒体去重、子板先于根板发布、失败逆序删除以及预检前零网络；生产 Taro 构建真实编译该依赖链。
- **生效范围：** 微信端公共板发布编排；cboard-api 无业务代码变更，不新增数据库 schema、路由或第二后端。真实生产 Blob、HTTPS、账号与公网发布仍需部署环境验收。

## 变动 3：家属专属入口与三重显式确认

- **意图：** 让公开贡献成为家属主动维护动作，防止患者误触、家庭照片误上传或用户误以为删除后能收回他人副本。
- **决策：** 发布面板只放在“照护设置 → 图片库维护”，并由结构测试禁止进入患者 `ExpressionWorkspace`。家属必须选择个人板、填写公开署名、分别开启“拥有公开权利”和“已移除患者隐私”两个开关，再通过最终模态框确认公开传播及副本不可收回；成功后只显示并复制 CBoard 公共板链接。
- **理由：** 家庭照片、声音和短视频具有高隐私风险，单个“发布”按钮不足以表达后果。把入口放在既有低频维护区并分开确认权利与隐私，比患者页快捷入口或默认上传更安全、更容易理解。
- **证据：** 页面放置和确认结构测试 2 条通过；小程序全量 `82 test files / 360 tests`、产物质量门 `10/10`、TypeScript、ESLint、`226 app / 32 CBoard core` 边界和 production build 全部通过。主包 `1,285,089 B`，各分包均低于项目采用的 1.5 MiB 预警线。
- **生效范围：** 微信小程序家属图片库维护页、发布状态与链接复制；不进入患者页，不自动执行真实发布，不替代公众平台性能扫描或物理真机隐私验收。

## 变动 4：复用 CBoard 所有者接口补齐发布后管理

- **意图：** 让家属不仅能发布，还能在微信查看同一账号的公共板、取消公开或永久删除，补齐公共贡献的可控生命周期。
- **决策：** 复用 CBoard “All My Boards” 的既有语义和 cboard-api `GET /board/byemail/{email}`、`PUT /board/{id}`、`DELETE /board/{id}`。微信按 100 条分页读取账号全部板，只显示 `isPublic=true`；取消公开把原板切回私有，永久删除单独使用红色确认并明确可能造成链接断开。列表同时管理 Web 与微信发布的板，不另建微信专属索引。
- **理由：** CBoard 已经实现所有者过滤、公开切换和删除，直接复用比新增发布记录表、专用撤回 API或第二套账号板列表更稳定。取消公开与删除的后果不同，必须拆成两个动作；他人已下载副本无法撤回也必须诚实提示。
- **证据：** 微信管理端口/服务/放置与原发布回归聚焦 `4 files / 13 tests` 通过；最终全量 `83 files / 365 tests`、质量门 `10/10`、TypeScript、ESLint、`228 app / 32 core` 边界与 production build 全通过。backup 分包 `649,483 B`，仍低于 1.5 MiB。cboard-api 既有所有权单元测试 `8 passing`，覆盖普通用户创建归属、所有者更新/删除、跨用户拒绝和管理员能力；现有 `/board/byemail` 集成测试源码覆盖用户读取自己成功、读取他人 `403`。
- **生效范围：** 微信“照护设置 → 图片库维护 → 发布公共沟通板”中的账号公共板列表、复制链接、取消公开和永久删除；复用现有 cboard-api，不修改 API、数据库或 CBoard Web。取消公开/删除只作用于选中的服务器板，不远程删除他人副本、本机个人板或其他子板；真实公网账号、Blob、弱网中断和物理真机仍待外部验收。
