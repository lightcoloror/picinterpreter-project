# 公共图卡逐图投稿上游源码审查

## 结论

本轮没有为图语家从零新建“逐图投稿、审核、申诉、撤回传播副本和运营队列”平台。

OpenSymbols 和 ARASAAC 都适合继续作为公共图卡搜索与取图来源，但当前公开源码及公开 API 均没有可由 CBoard Web 或微信小程序直接复用的公众逐图投稿审核闭环。图语家继续保留已经完成的“整块 CBoard 公共沟通板受控发布”，逐图投稿能力保持独立延期，直到出现成熟、公开、可运行且许可边界清晰的上游契约。

## 变动 1：固定并运行两个官方上游

- **意图：** 判断“逐图公共图库投稿仍未实现”究竟是遗漏，还是上游生态确实没有可直接复用的成熟模块。
- **决策：** 固定审阅 `open-aac/opensymbols` 提交 `6469116eb08b654acca7e6a3dfa172d679ada621`，以及 `Arasaac/public-api` 提交 `722c6b2e45e9241b7f8389955abe932dcad24b0d`。只在隔离源码副本中安装、构建和测试，不改图语家运行代码。
- **理由：** 仓库介绍和接口名称不足以证明投稿闭环；必须检查公开路由、鉴权、控制器、模型、测试和实际运行状态。
- **证据：** OpenSymbols 本地源码位于 `D:\used-by-codex\source-reviews\picinterpreter-public-pictogram-contribution-20260728\opensymbols`；ARASAAC Public API 位于同级 `arasaac-public-api`。两个仓库均为 MIT 许可；固定提交、当前路由和测试结果均已读取。
- **生效范围：** 图语家公共图库能力选型、源码账本和覆盖矩阵；不代表把两个上游整体嵌入 CBoard，也不授权使用各图卡资源自身的独立许可。

## 变动 2：OpenSymbols 只作为搜索与许可来源复用

- **意图：** 防止把 OpenSymbols 内部管理员接口误写成面向患者家庭的公众投稿接口。
- **决策：** 继续复用公开图卡搜索、来源归因和许可元数据；不调用管理员 `repositories`、`symbols` 写接口，不依赖空的 `requests` 控制器建立投稿流程。
- **理由：** `Api::SymbolsController` 的更新、安全标记、肤色、排序和默认图操作，以及 `Api::RepositoriesController` 的写路径，均经过 `require_authorization` 并要求管理员令牌；`Api::RequestsController#create/index` 没有实现。公开网站只提供搜索 API，并把新符号提交描述为未来计划或人工联系流程。
- **证据：** `ApplicationController#require_authorization` 在非管理员情况下返回未授权；`config/routes.rb` 虽声明写路由，但对应写控制器受管理员保护，`requests` 动作为空。上游 README 说明项目代码为 MIT，图卡结果仍逐项携带各自 license/author/source。
- **生效范围：** cboard-api 的 OpenSymbols 搜索、图片代理和许可展示可继续使用；不新增公众上传入口、审核后台、申诉或自动公开。

## 变动 3：ARASAAC Public API 只作为只读图库参考

- **意图：** 确认 ARASAAC 是否已有可直接复用的图卡投稿写 API。
- **决策：** 保留当前搜索、取图、语言和排序能力参考；不把素材读取、短语纠错报告或内部 Mongo 模型包装成图卡投稿。
- **理由：** `openapi_v2.yml` 的 pictograms、users/profile 和 materials 路径全部是 `GET`；v1 唯一相关 `POST` 是 `/phrases/report`，用途是报告自然语言转换错误，不是创建图卡。源码中的 `Pictograms` 模型并不等于公开创建协议。
- **证据：** `npm ci` 与 `npm run build` 真实通过。默认测试入口首先因旧版 `mongodb-memory-server` 拒绝 HTTPS 下载而失败；改用只绑定 `127.0.0.1:27000` 的隔离 Mongo 4.4 后，模型套件通过，控制器套件仍因当前路由装配返回 `404`，最终为 `1 passed / 3 failed suites`、`3 passed / 5 failed tests`。临时容器已删除。构建更新了仓库内两份派生 OpenAPI JSON，未把这些生成差异带入图语家。
- **生效范围：** ARASAAC 继续作为读取型公共图源和架构证据；不把上游测试失败归因于图语家，也不把构建成功冒充投稿能力完成。

## 变动 4：固化许可、隐私和审核进入条件

- **意图：** 避免为了补齐矩阵状态而把家庭照片、患者声音或来源不明素材直接公开。
- **决策：** 逐图投稿只有在同时满足以下条件后才进入实现：存在成熟上游提交 API；有贡献者身份、素材级许可和可撤回状态；有人工审核、敏感内容处理、申诉与运营队列；公开副本传播边界可明确告知；客户端仍需显式人工确认。
- **理由：** 逐图投稿是内容治理系统，不是增加一个上传按钮。家庭媒体含患者隐私，图卡本身可能使用不同许可；没有审核和撤回语义时，自动公开会造成不可接受的安全与合规风险。
- **证据：** 当前 CBoard 已完成整板私有占位、媒体去重、子板先发布、根板最后公开、失败回滚、权利/隐私/最终确认及账号所有者取消公开/删除；这些能力解决“受控分享一块板”，但不提供逐图公共库治理。
- **生效范围：** CBoard Web、cboard-api、微信小程序和未来公共图库服务；不影响本机自定义图卡、缺词私图、在线候选人工确认、结构化图库导入或整板公共发布。

## 后续动作

1. 继续使用当前 CBoard 整板公共发布闭环作为可运行贡献方式。
2. OpenSymbols 与 ARASAAC 继续用于搜索、取图、来源和许可，不调用非公开写接口。
3. 若上游未来发布公众提交 API，先重新拉取固定提交、运行测试并审查身份、审核、撤回和许可契约，再做薄适配。
4. 在此之前，不新增第二套投稿数据库、运营后台或假审核状态。
