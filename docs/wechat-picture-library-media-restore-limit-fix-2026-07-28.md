# 微信图库备份声音与视频恢复限额修复

## 结论

图语家微信小程序原有 `PictureLibraryArchive v1` 已支持图片、图卡录音和短视频跨设备恢复，但恢复阶段的媒体总量计数存在分支错误：声音没有计入声音总量，视频却同时计入视频与声音总量。本轮不新增格式、依赖或 UI，只修正既有安全门并用真实 ZIP 解压恢复回归证明边界。

## 变动 1：复用既有归档契约修正媒体总量计数

- **意图：** 防止恶意或异常备份通过大量单文件合法录音绕过 20 MiB 声音总量限制，同时避免合法视频被错误地消耗声音额度。
- **决策：** 保持单声音 5 MiB、声音合计 20 MiB、单视频 8 MiB、视频合计 40 MiB 的现有数值不变；在 `sounds/` 分支累加并检查 `totalSoundSize`，在 `videos/` 分支只累加并检查 `totalVideoSize`。
- **理由：** 图片、声音和视频已经通过 CBoard `TileDTO`、Open Board 兼容媒体语义、`PictureLibraryArchive v1` 与微信文件端口形成闭环，真正缺陷只是两行计数落在了错误分支。最小修复比新增归档格式、第三方媒体库或第二套恢复器更可靠。
- **证据：** 修复前源码显示 `totalSoundSize += data.byteLength` 位于视频分支，声音分支没有总量累加；修复后两个媒体种类分别维护独立额度。
- **生效范围：** 微信图片库 ZIP、完整本机 ZIP和两个端侧加密私有快照解密后的恢复阶段；不改变导出格式、单文件限额、图片恢复、冲突策略、患者 UI、账号 API 或 CBoard Web。

## 变动 2：增加真实 ZIP 解压与事务回归

- **意图：** 防止只用小型 fixture 验证格式正确，却无法发现累计额度串线。
- **决策：** 继续复用现有 JSZip 测试夹具、fflate 生产扫描器、共享 manifest 和事务 restore session；新增两个恢复场景：5 段各 `4 MiB + 1 B` 的合法 MP3 合计超过 20 MiB 时必须拒绝并保留本机板；3 段各 7 MiB 的合法 MP4 合计 21 MiB、低于 40 MiB 时必须成功恢复且保留 merge 语义。
- **理由：** 小数组或直接断言变量不能证明 ZIP 条目大小、媒体签名、批次解压、累计额度、暂存清理和最终板写入共同成立。真实压缩归档能覆盖完整生产路径，同时压缩零填充 fixture，避免把大二进制加入仓库。
- **证据：** 聚焦 `1 file / 22 tests` 通过；全量 `83 files / 367 tests` 与质量门 `10/10` 通过；TypeScript、修改文件 ESLint、`229 app / 32 CBoard core` 边界通过。production build 成功，main `1,285,089 B`、backup `649,483 B`，所有分包低于 1.5 MiB。首次 Vitest 在受限 Windows 沙箱因 Vite `spawn EPERM` 未启动，沙箱外同命令通过；Prettier 未安装，因此未新增依赖，继续以项目既有 ESLint 为格式门。
- **生效范围：** 微信备份服务及其回归门；不把单元/构建结果冒充两台物理手机、低存储、系统文件选择或真实云恢复通过。

## 变动 3：官方微信运行环境只读复核

- **意图：** 确认修复期间没有引入当前 production 模拟器错误，同时遵守后台操作和不置顶要求。
- **决策：** 使用官方 WeChat DevTools Skill `0.3.5` 只读检查登录、当前页面、系统信息、console 和 network；不刷新、不清 storage、不预览、不上传。
- **理由：** 恢复限额是后台事务，不需要为了证明它而修改用户模拟器数据；只读诊断足以确认当前构建没有伴随运行异常。
- **证据：** Skill 与客户端版本关系 `equal`、登录有效、无需 token；当前页为正式患者页，iPhone 12/13 Pro 竖屏安全区可读；console 没有 error，网络没有 4xx/5xx。Skill 0.3.5 不提供方向切换工具，因此未把竖屏模拟器证据冒充 #14/#67 横竖屏真机验收。
- **生效范围：** 本轮运行环境证据和工具边界；不改变开发者工具窗口状态，不替代真机旋转、触控、断网和媒体恢复。
